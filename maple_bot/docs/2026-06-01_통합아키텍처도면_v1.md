## 0. 확정 전제 (1~4단계 합의)

### 표준 기둥 6
1. 단일앱 + god-loop를 "오케스트레이터 + 플러그형 모듈"로 분해
2. config.json 중앙집중 + 런타임 상태를 명시적 상태머신 클래스로 추출
3. 동선 = "블록 시퀀스" 데이터 모델 (A zones + C 블록/녹화, B 고정슬롯 폐기)
4. 거탐 = Planet v2 코어 / 3.13 사이드카 프로세스 / 거탐엔진 인터페이스 격리 / 신규(비올레타) 꽂기식
5. 알림 = 텔레그램 모듈 신설
6. 인간화 계층(Humanizer) = 입력 직전 단일 통제점 (C 모델 채택)

### 헌법 (불변 원칙)
- **화면인식 + Interception + Humanizer만 사용.**
- **메모리 조작(pymem / ReadProcessMemory / WriteProcessMemory) 전면 배제.**
- 모든 행동은 Humanizer를 통과한다. 고정 상수 타이밍 직접 입력 금지.
- 외부 블랙박스(거탐 코어)는 반드시 인터페이스 뒤에 격리한다.

### 기반 확정
- 본체 Python 3.14 / 거탐 사이드카 Python 3.13
- 입력 백엔드 Interception(주) + 소프트웨어(폴백)

### [카테고리 2] 동선/이동 — 분석 완료

**A (map_navigator.py 직독)**
- `_do_jump`: 점프 `_rnd(0.083~0.127)` — 타이밍 랜덤화 되어있음(기계적이라는 오진단 정정)
- `_do_climb`: CLIMB_DURATION 2초 무조건 등반, **도착확인 폐루프 없음** ← 부자연 원인①
- `map_navigator` + `floor_hunt`(bot_loop 내장) **2개 동선엔진 경합** ← 부자연 원인②
- 이동수단 walk+밧줄점프만, **텔레포트 없음** ← 부자연 원인③

**C (coord_script_runner.pyc — dis 확정)**
- `CoordScriptRunner(engine, actions, log, loop)`: action dict 리스트 순차 실행기
- action 스키마: `{"type":"move","x":35,"move_type":"walk|teleport","direction":"left|right"}`
- `_teleport_to_x`: 거리>15px면 space 텔포, 이하 walk 폴백 (사람같은 혼합 이동)
- `_walk_to_x`: TOLERANCE 3px 폐루프로 좌표 수렴
- 데이터 기반 → 코드수정 없이 블록 추가로 확장

**B (관찰 — Themida 봉인)**
- 고정 좌표슬롯(구역20·상하텔포10·포탈9·방향컨트롤10), 텔포블락해제 보유
- 코드 직독 불가, config.ini·UI로 동작만 확정

**채택 결론**
- C의 CoordScriptRunner(action dict + 거리별 텔포폴백 + TOLERANCE 폐루프)를 동선 표준 모델로 채택
- B의 텔포블락해제·포탈을 action 타입으로 흡수(동작 재현)
- A는 floor_hunt 층판별 로직만 계승, 단일 엔진 통합(이중경합 제거), 도착확인은 C 폐루프로 해결

### [카테고리 1] 연결/인식 — 분석 완료

**캐릭터 위치 감지**
- A (minimap_reader.py 직독): RGB 거리매칭(char_r/g/b ± tolerance) + 최소4px + 무게중심. 조명/배경색에 취약
- C (vision.py dis 확정): HSV inRange(노랑) + min_area~max_area contour 면적필터 + moments 무게중심 + set_hsv_override(맵별 색조정) + 드래그/고정 좌표 둘 다
- → C가 견고. A RGB매칭 실패가 "위치 미감지→3초 좌우흔들림" 폴백의 근본 원인 추정

**다른 유저 감지**
- A: anti_mob 등 산재
- C (scanner.py dis 확정): 전용 UserScanner 백그라운드 스레드. HSV 빨강(타인)/노랑(본인) 구분, MIN_RED_PIXELS, GONE_CONFIRM_SEC(이탈 N초 확인 후 발화→깜빡임 오탐방지), 이벤트큐(EVT_DETECTED/USER_GONE), MAP_RED_*_OVERRIDE 맵별 보정
- → C UserScanner 설계 우수

**몬스터 감지**
- A (detector.py 직독): YOLO + cv2.matchTemplate(TM_CCOEFF) + 학습모델/캡처툴 보유
- C: HSV 색기반(YOLO 미확인)
- → A 우위, C HSV는 폴백 가치

**채택 결론**
- 캐릭터 위치: C HSV+면적필터+오버라이드 채택, A RGB 폐기 (동선 자연스러움과 직결)
- 다른 유저: C UserScanner 전면 채택 (전용스레드+빨/노 구분+GONE_CONFIRM)
- 몬스터: A YOLO+템플릿 유지 + C HSV 폴백
- 미니맵 영역설정: A+C(드래그+고정 둘 다)

## 5-3. 모듈/컴포넌트 구조도 (승인됨)

### 설계 원칙
1. god-loop 해체: bot_loop._run() 1700줄 → 오케스트레이터 + 독립 모듈
2. 감지(Sensing)와 행동(Acting)을 이벤트큐로 분리 (C EVT_DETECTED 패턴)
3. 모든 행동은 Humanizer 단일 통제점 경유
4. 외부/봉인 엔진(거탐)은 인터페이스 뒤 사이드카 격리

### 계층 구조
- UI(PyQt6, 6카테고리) → config.json 읽기/쓰기만
- ★ORCHESTRATOR: 모듈 생명주기 + 이벤트큐 소비 + 우선순위 판단 + 상태머신
- SENSING(독립스레드+이벤트큐): CharScanner/UserScanner/ChatScanner/MonsterDet/PotionScan/MinigameWatcher
- ACTING: Combat/Buff/Pet/Potion/JunkSell/Charlie
- NAVIGATION: BlockRunner(action시퀀스) + FloorJudge(층판별+도착확인폐루프)
- ★HUMANIZER: 지터·반응시간·불완전성·드리프트 (입력 단일통제점)
- INPUT BACKEND: Interception(주)/SendInput(폴백)
- MINIGAME SOLVER(인터페이스): PlanetV2(사이드카)/Lona(옵션)/Violeta(미래) — mmap IPC 3.13
- FOUNDATION: ScreenReader/ConfigManager/License/Updater/Telegram/Logger/HotkeyManager

### (a) 독립 동작부 (죽어도 전체 안죽음)
- 각 Scanner: 자기 ROI만 캡처→판정→이벤트큐. 서로 모름
- MinigameSolver 사이드카: 별도 프로세스, 죽어도 사냥 계속(B·C 실증)
- Telegram/Logger/Updater: 부수효과만
- JunkSell/Charlie: 트리거시 독립 시퀀스

### (b) 유기적 연결부 (협력 필수)
| 연결 | 매개 | 결합도 |
|------|------|------|
| Scanner→Orchestrator | 이벤트큐 | 느슨 |
| Orchestrator→Navigation/Acting | 명령 호출 | 중 |
| Navigation+Acting→Humanizer | intent 객체 | 강제경유 |
| CharScanner→Navigation | 공유 위치상태 | 폐루프 |
| Orchestrator 내부 | 상태머신(거탐>판매>사냥) | - |

핵심 3원칙: 감지=이벤트큐(느슨), 행동=Humanizer강제경유, 위치=폐루프

### god-loop 분해 매핑
| A god-loop if블록 | → 통합 모듈 |
|------|------|
| 안전감지 | MinigameWatcher 스레드→이벤트큐 |
| 픽업타이머 | Orchestrator 타이머→Charlie/Pickup |
| floor_hunt 상태머신 | Navigation(BlockRunner+FloorJudge) |
| 공격/버프 | Acting(Combat/Buff) |
| 포션체크 | PotionScanner 스레드 |
| 산재한 key_up/down | 전부 Humanizer 경유 |
→ 1700줄 단일함수 → 각 200줄이하 모듈 + 얇은 오케스트레이터

## 5-4. 데이터 흐름도 + 인터페이스 계약 (승인됨)

### 데이터 흐름 3종
① 정상 사냥(매 프레임): Scanner들 mss.capture(ROI) → CharScanner(x,y)→공유위치→BlockRunner 폐루프 / MonsterDet→Combat. Orchestrator cmd→Nav/Acting→intent→Humanizer→InputBackend→게임. 단방향 파이프라인 + 위치 폐루프 1개
② 안전 이벤트: MinigameWatcher스레드→EVT_DETECTED→이벤트큐→Orchestrator 소비(우선순위 거탐>사냥)→Acting/Nav 일괄 pause(Humanizer key_up)→MinigameSolver.solve(mmap IPC→3.13사이드카)→완료신호→사냥재개. ※god-loop if폭탄 대체
③ 설정: UI→config.json→ConfigManager→각 모듈 주입. UI는 로직0

### 인터페이스 계약 5종 (=콘센트 규격)
① Scanner: start(event_queue)/stop. 출력 Event{type,data,ts}. 추가/교체해도 Orchestrator 무수정
② MinigameSolver: can_handle(type)/solve(screenshot,ctx)→SolveResult{success,elapsed,note}. planet/lona/violeta 같은 계약
③ Navigation: set_route(blocks)/step(pos)/is_arrived(). Block{type,target_x,move_type,direction}=C routine_runner 스키마
④ Humanizer: perform(Intent). Intent{action,key,base_hold_sec,base_delay,risk_profile}. 모든모듈은 Intent만, 언제·어떻게는 Humanizer 독점
⑤ InputBackend: key_down/up/press. Interception|SendInput 교체가능

### 핵심 데이터 객체 4
- Event(감지→오케스트레이터, C이벤트큐) / Block(동선1스텝, C스키마) / Intent(행동→Humanizer, 신규) / SolveResult(거탐결과, 신규)
- 모듈간 데이터가 이 4개로 수렴
